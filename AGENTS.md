## 0x00. Importance

All changes generated by Large Language Models (LLMs) MUST be reviewed and approved by a **human** before being committed. The commit message MUST include an explicit confirmation of this review.

Example:
```text
Add Documents

This commit generated by AI. All changes authored by me.

Codex with GPT-5.5
Prompt:
Your job is trying to add documents in this swift package project.
- You should use Apple DocC format;
- You should add README.md;
- You should add doc for every swift file in @/Sources  ;
```

## 0x02. Policy

### Document Policy

- Rewrite documentation, don’t patch it.  
  Rework the structure and logic as a whole. Keep the main flow concise and easy to scan, with necessary details placed where they don’t interrupt reading.

### Coding Policy

- Understand the data first.  
  Before coding, understand where the data comes from, how it is transformed and used, and whether it is persisted.

- Review before implementation.  
  Start a subagent to check the proposed approach against best practices.

- Rewrite instead of patching.  
  Prefer a clean implementation over workarounds, while safely migrating persisted data.

- Preserve the design intent.  
  Let the design guide implementation choices. Never hide errors or fail silently.

- Maintain one source of truth.  
  Identify the authoritative data source and eliminate redundant state, transformations, and processing.

- Document contracts and boundaries.  
  Focus on data definitions, transformations, architecture, protocols, and module boundaries. Keep implementation details secondary.

- Make behavior observable.  
  Add structured logs at responsibility boundaries and key processing points. Without logs, issues cannot be traced or diagnosed.

## 0x04. User-Facing Feature Documentation

- Any change that adds, removes, or changes user-visible behavior must update `docs/FEAT.md` in the same change.
- Keep `docs/FEAT.md` focused on what users can do. Lead with the Happy Path, then introduce advanced capabilities progressively as users explore further.
- Invoke the `$i-have-adhd` skill whenever writing or revising `docs/FEAT.md`. Apply it to the document's reader-facing structure and wording, not only to the assistant response.
- Before adding content, review the complete `docs/FEAT.md`. Improve nearby wording, merge overlapping explanations, and remove stale or redundant content instead of only appending another section.
- Keep the document concise and user-facing. Avoid implementation details and do not duplicate exhaustive setup or reference material from `README.md`.


## 0x05. Glossary

`docs/Glossary.md` is the single source of truth for **what things are called**. It governs wording, not implementation.

No implementation detail of any kind: no bundle identifiers, file paths, environment variables, module or target names, API shapes, or code samples. 
If a line would only make sense to someone reading the source, it does not belong here.

### When to update it

- Before writing any user-visible string, read it first and reuse the existing wording rather than inventing a synonym.
- Whenever a new user-visible concept, component, or state appears, add its name in the same change.
- Whenever a name is changed or retired, update the entry and move the old name into the banned-words list — do not silently delete it, so the reason stays visible.
- When `docs/FEAT.md` or any feature doc introduces a term not yet listed, add it to the glossary in the same change.

## 0x07. Changelog

`CHANGELOG.md` records each release, grouped by feature module.

### Structure

- `##` = version. `[Unreleased]` first, then `[x.y.z] - YYYY-MM-DD`, newest first. Compare links at the bottom.
- `###` = feature module, never an app.
- Same module, different behavior per app → prefix the entry with the app: `[Halo] - XXXX`. Uniform or single-layer entries carry no prefix.

## 0x08. Activities

在 [ACTIVITIES.md](./ACTIVITIES.md) 中记录当前任务，使未参与对话的人也能理解用户要什么、已经明确什么、当前讨论什么。
注意 ACTIVITIES.md 放入 gitignore 。

任务的开始与结束由用户决定。

记录时机：
- 用户对当前任务有新的明确表达或确认时记录。
- 问题与讨论目标无需等到形成决定后才记录。
- AI 建议经用户采纳后，记录最终决定。
- 用户的实际行动可以表明采纳，无需口头确认；采纳范围仅限该行动直接体现的选择。

内容准则：
- 忠实：
  只记录用户明确表达或确认的需求、问题、讨论目标、提供的材料、目标产出、约束和决定。
  不记录 AI 自行提出的建议、推测、分析、后续计划、待确认问题或例行状态。
- 完备：
  保留理解任务必需的具体事项、条件和范围，以及用户明确给出的理由、判断依据和完成要求。不能只留下名称、目录或笼统概括，不能因精简而丢失必要信息。
- 准确：
  保持问题、想法、反馈与决定各自的性质，不把推测当事实、讨论当决定，不补全用户未说明的内容。
- 有界：
  保持信息原有的适用范围与条件。
  临时要求不自动成为永久规则，局部选择不扩大为整体决定；长期规则须以用户明确表达或确认为依据。

维护原则：
- 合并同一事项的重复信息。同一事项、同一适用范围内，以用户最新的明确表述为准。
- 持续判断信息是否仍然适用，让过期、撤回或已被替代的信息退出当前有效上下文，同时保留理解现有决定所需的依据。
- 无法判断的信息保留其不确定性，不自行认定有效或失效。
- 与项目文档保持一致。已在项目文档中记录的内容，不在 ACTIVITIES 中重复抄写。
- 通过合理分项、去重和精简保持易读，不逐轮记录流水账。没有新增或变更时不更新。

结构规范：
  按主题归类，按具体事项分项。每个条目只承载一个明确事项；
  不同的问题、约束或决定拆为同级条目，
  避免堆在“当前任务”等笼统条目中。

格式：

```md
# <任务名称>

- <明确事项>
  <简短的必要说明>
```

## 0x09. 交付前验证

内容：代码与单测不能代表实际用户体验，在确认任务完成前，以用户视角进行用户验收测试。

目的：确保用户满意度、降低风险、符合业务需求。

注意：若遇到卡点而无法执行，请重点声明，而不要静默忽视。

准备：明确验证意图，准备最初的需求，不要包含臆想的含糊内容。以简短的自然语言在报告中体现。

以证据为准，给出截图或录屏以供用户判断，同时在报告时明确区分"已验证"和"未验证"。
